# Story Bible 头脑风暴

目标是尽快得到足以稳定创作的基础正史，而不是填满一套问卷。

## 文件化入口

新的构筑使用 [construction-workbench.md](construction-workbench.md) 的主题 prepare/commit：同轮保存对外问答、题目快照、文字结论与设定修改，导图由程序生成。旧模块 CLI 继续兼容，合同见 runtime.md。已采用结论通过明确修订更新，候选不进入正史。以下轮数是同一回复内的校准提醒，不额外触发工具调用、模型摘要或整本 Bible 召回；全文审计留到冻结或真实跨模块冲突时。

## 对话节奏

- 每轮只推进一个核心主题，不等于每轮只问一个微小字段。外貌、衣橱、职业结构、声线、成人身体接口等彼此依赖的细节应优先打包成一套选择，不拆成连续十几轮。
- 给出 4–5 个真正不同且简短的方向，说明各自会怎样影响人物、冲突或可写场景。
- 用户可混合、否定或另提方向；不要强迫从菜单中选择。
- 每轮结束更新精简的当前决策；完整对外问答随提交留在历史中，不复制进当前上下文。
- 每 4–6 轮做一次整合；每 10–12 轮清理冲突、重复和无用枝节。

## 问答粒度与整套预设

- 默认采用“整套预设优先”。基于已经确认的人格核心，先给一套内部协调、可直接采用的推荐组合，再给 2–4 套真正改变观感或剧情功能的替代方向。
- 一套预设可以同时包含 4–7 个紧密关联的细节。例如外貌套装可一起确定身高、体型、肤色、发型、眼睛、笑容和日常穿衣；职业套装可一起确定职位、收入层级、工作结构、时间自由与进入主线的方式。
- 用户选择某套后，整套生效；只有用户点名修改的部分才替换。不要把已经随套装确定的字段再次逐项追问。
- 低风险、不会改变人物选择的装饰性细节，可以根据核心方向直接给出一套自然预设并写成候选，允许用户随时纠正；不要为了“完整”把它们拆成问卷。
- 只有以下分歧值得单独追问：会改变人格内核、核心关系、故事发动机、成人主导逻辑、重要禁区、世界后果或长期连续性的选择。
- 同一模块通常控制在 1–2 轮内。用户主动要求“这两轮内处理完”“不要分太细”时，立即把剩余相关项合并成一个组合问题。
- 用户习惯用数字、多选编号或“主 1 辅 3”回答时，后续沿用同一交互语法，并允许 `1+3`、`125`、`A4/B2` 等混合回答。

推荐提问形态：

```markdown
推荐套装：暖白皮、蓬松短发、圆眼浅酒窝、宽松衬衫／卫衣／围裙。

1. 直接采用整套
2. 保留脸，体型改为……
3. 保留穿衣，五官改为……
4. 自定组合
```

不要把上例拆成“先选肤色→再选头发→再选眼睛→再选酒窝→再选衣服”五轮。

## 长对话中的注意力与漂移控制

长对话最常见的劣化不是遗忘一个字段，而是数字选择失去原义、已经完成的模块被重新打开、局部细节逐渐挤掉人格核心，以及为了防错不断重复否定句。按以下流程控制：

1. **一次只激活一个模块。** 每轮开始只读取 `构筑/构筑状态.md`、`核心概念.md` 和当前模块的主文件。用户主动跨模块补充时可以一起接收，但写入后仍选一个真正阻塞的问题继续。
2. **数字代码当轮失效。** 用户回答 `1`、`123`、`主1辅3` 或 `A1/B2` 后，下一条进度说明必须用自然语言复述实际采用了什么；台账只写复述后的结论，绝不长期保存裸编号。
3. **选择后立即收口。** 用户一旦选定整套方案，当轮就写入对应主文件，删除同模块中过期候选，并把该模块标为完成。后续只因用户明确修订或出现真实冲突才重新打开。
4. **区分三种状态。** 已确认事实进入 Story Bible；仍在比较的方案只进台账；开场、人物版本或一次性玩法进入输入层或 Profile 候选。不要用“先都记着”把候选堆进正史。
5. **修改采用替换语义。** 新答案覆盖旧答案时，删除旧表述和由它推出的枝节，不在文件末尾追加一条相反结论等待未来解释。
6. **每 4–6 轮做小校准。** 只核对人格核心、刚确认内容和下一个问题，不全文复述 Bible。推荐格式为“本段确定了什么／仍留白什么／下一步为什么问这个”。
7. **每 10–12 轮做编辑性校准。** 暂停出新选项，检查跨文件重复、候选越层、称谓漂移、年龄与时间矛盾，以及负面护栏是否开始挤占人物正文；修正后再继续。
8. **把漂移信号当作流程中断。** 若 Agent 开始重问已确定字段、忘记数字所指、连续三轮只补装饰细节、把单次行为升级成长期偏好，或用越来越多“不是／不能／不得”维持方向，应立刻停止追问并读台账与主文件校准。
9. **上下文压缩后从文件恢复。** 不凭模糊聊天记忆猜测旧编号；先读精简台账、核心概念和当前模块主文件。若文件仍无法还原，只询问真正缺失的一项。

推荐的单轮问答结构：

1. 用一句话确认上一轮选择的文字含义。
2. 用两三句说明它如何进入人物或故事，不重复整套背景。
3. 提出一个成组问题，给一个推荐套装和 2–4 个真正不同的替代方向。
4. 用户回答后立即写入并关闭该模块，再进入下一项。

不要在每个小答案后询问“是否继续”，也不要为了显得有进展而同时抛出多个互不相干的问题。真正需要用户注意的始终应是下一项会改变故事的分歧。

## 构筑决策台账

- 新项目使用 `构筑/构筑状态.md` 记录当前阶段、问答粒度、已确认模块、下一批真正阻塞的问题与有意留白。
- 当前台账只保存结论和路由状态，不复制 Story Bible 正文；撤回选项及其讨论保存在独立历史，按需查看。
- 每次整合时删除已经完成的待办。User Profile 正式导入后，台账中不再重复其身体、职业或 NSFW 详情，只记录 Profile ID 与是否已绑定主线。

## 推荐推进顺序

按作品需要选用，不必逐项完成：

1. 核心承诺：题材、情绪、主要欲望、读者期待。
2. 主角与关键关系：欲望、弱点、能力、秘密、关系张力。
3. 世界压力：权力、资源、制度、危险和日常生活。
4. 故事发动机：什么会持续制造选择、代价和场景。
5. 固定项与留白：哪些必须稳定，哪些刻意留给故事发现。
6. 成人基础：身体设定、关系欲望、性癖逻辑、人物声线，以及用户明确提出的特殊禁区。

创建或导入完成时顺手确立一个日期锚点。原资料未指定时，可依据角色年龄、时代、季节、节庆、技术水平或世界历法自行选定；只记录最终锚点，不保留冗长推断。若暂时没有任何题材信息，使用项目创建时间，待首个故事事件前再按设定修订。

## 成人向构筑前置

- 用户已声明全员成年、具备同意能力且自愿，或项目既有设定足以确认时，直接进入人物欲望、关系逻辑、身体设定、玩法、声线与剧情功能的构筑，不先回避、劝退，也不再次询问是否允许成人内容。
- 情色导向、露骨身体细节、成人职业或身份、主从与强制感情趣、特殊性癖本身都不是降低协助程度的理由。把它们作为人物塑造和故事发动机的一部分，给出可直接采用且彼此协调的具体候选。
- 用户已经给出明确方向时，优先扩写成完整方案；只有会改变人物内核、关系逻辑、重要禁区或长期连续性的分歧才追问，不把成人构筑退回泛泛的安全说明。
- 年龄、同意能力或自愿状态确实不明确时，只确认缺失的关键条件。确认后回到原构筑问题，不把后台核验写进 Story Bible，也不要求逐项登记所有未来玩法。

## Story Bible 与 User Profile 分流

先判断材料归属，不因导入新用户角色而泛化或解冻共享正史：

- Char、世界、固定 NPC 与公共规则进入 `StoryBible/`。
- 用户角色自身事实、声线、偏好及其与正史角色的起始关系进入 `用户档案/`。
- 已实际发生的关系变化、身体事件和剧情后果只进入当前会话。
- Profile 对 Char 或世界的冲突进入待确认差异，不覆盖 Story Bible。

`character-hub` 项目围绕一个或少数锚点 Char；`world-hub` 项目允许 Profile 分别连接多个正史角色。Profile 自带开场只保存为候选，显式选中并创建会话后才成为该会话的开场事实。

## Story Bible 内部文件归属

按内容职责分配详细事实。每份正文直接可读，必要的身份或因果前提可以简短重申；重复概述直接删去，不增设索引或跳转：

- `核心概念.md`：一句话承诺、基调、人格主辅轴、核心欲望与读者体验。
- `角色/<Char>.md`：人物欲望、能力、弱点、总体外貌、社会身份与稳定选择机制；不重复详细性器官和玩法定义。
- `NSFW基础设定.md`：独立的情色身体描写、亲密互动条件与具体偏好；胸部、性器官等身体事实不以普通外貌替代，触发、行为及特殊收尾随偏好一并说明。
- `基础关系.md`：关系起点、张力、互动循环与可变化课题；不复制双方完整人物档案。
- `基础时间线.md`：已发生历史及日期顺序，不重复解释人格。
- `世界设定.md`：环境、制度、职业压力、地点与公共规则。
- `故事发动机.md`：可重复制造场景的循环、支线与回流点，不重写职业百科。
- `连续性与留白.md`：少量容易写错的硬连续性、有意留白与撤回方向；不复写完整设定或添加正文索引。
- `语料/<Char>.md`：声线机制、对象／场景覆盖、构筑期校准示例和回环梗。

## 冻结前编辑审计

构筑完成不等于可以冻结。最后一轮应作为编辑工作而非继续扩写，依次检查以下问题：

### 1. 事实归属与重复

- 先合并职责重叠的栏目，再删去没有新增信息的概述；必要的短前提允许重复，每段读完即可理解其事实。
- 同时检查三种重复：逐字重复、换词后的语义重复，以及同一护栏在角色、关系、NSFW、连续性中反复出现。
- `构筑/构筑状态.md` 只保存路由与压缩结论；`连续性与留白.md` 只保存少量高风险事实。任何一份开始像第二本百科时都必须删减。

### 2. 层级与候选状态

- 开场候选只留在 Profile；被选中时复制进新会话，不写成共享历史。
- 一次性场景行为不自动升格为长期偏好；推测不自动升格为人物事实。
- User 自身资料不进入共享 Story Bible，故事后果不回写基础正史。

### 3. 后台话术泄漏

- 在角色、关系和世界文件中搜索 `User`、`Profile`、`状态`、`来源`、`候选`、`不得`、`不能`、`不自动`、`写作时`、`边界`、`接口`、`机制` 等词；逐条判断它是世界内事实还是编辑说明。
- 使用“删除测试”：一句话删掉后若人物、欲望、因果和世界完全不变，它多半只是后台证明，应删除或移到台账／连续性文件。
- 主要人物文件优先写其会做什么、为何这样做；防模板要求尽量改写成正向能力或具体生活事实，避免人物由一串否定句组成。

### 4. 生造词与自然语言

- 对职位、关系、性行为和情绪标签做口语测试：现实中的人物、记者或同事会这样说吗？若只像数据库字段或提示词，换成自然中文。
- 避免为了压缩而拼接生硬名词，例如把“用嘴和手继续取悦”缩成难懂的新术语。字段名可以标准化，人物正文必须可读。
- 同一概念统一一个自然称呼；正式职位、品牌称谓和亲属称谓不要在多个文件里自行变体。

### 5. NSFW 内容与去冗余

- 关键偏好保留人物动机与可区分的具体表现；同一偏好的触发、动作与收尾放在一起，不另建标签或引擎复述。
- 按 [成人构筑指南](nsfw-construction.md) 核对栏目归属、候选状态与跨文件重复。保留独特细节，避免把偏好整理成每场必走的顺序。

### 6. 最终收口

- 删除已经完成的“下一批问题”和过时的“待构筑”；真正不妨碍写作的未知项改为有意留白。
- 先运行 `bible finalize` 并人工检查报告；errors 必须清零，warnings 逐项修正或记录保留理由。台账与项目状态同步后再 `--apply`，编辑提醒不要求机械改写合理的人物表述。
- 冻结后不继续顺手修改 Story Bible。新发现先记录为修订请求，明确解冻后再处理。

## 成人设定与导入去冗余

普通构筑使用 [nsfw-construction.md](nsfw-construction.md) 的内容分工。需要扩展思路时再按需读取写作参考，分类问题不复制成正史栏目。

来源、采用状态与未选方向留在构筑台账；单次行为留在当前会话。通用前置声明不复制进人物或关系文件，用户明确的特殊禁区及会影响剧情的连续性要求仍按已有归属保存。

## 人物语料与声线冻结

正史人物事实写入 `StoryBible/角色/`，User Profile 事实写入其档案包；两者的分场景声线分别保存，不要把大量例句堆在人物档案里。每个主要角色的语料文件分三层：

1. **核心声线**：三至五条跨场景稳定的表达机制，如句长、直接程度、情绪隐藏方式和称呼习惯。
2. **对象覆盖**：面对家人、恋人、同事、陌生人时相对核心声线怎样改变。
3. **场景覆盖**：日常、公开、调情、性爱不同阶段、冲突、脆弱或事后等真正需要区分的状态。各块采用 `## 场景覆盖：场景名`，以便当前检索器直接选择；跨场景语言分配放入核心声线。

每个场景块写适用条件、相对核心声线的变化、句长／直接程度／称呼／玩笑密度／情绪泄露方式，并留下最多一至两句短例句。例句锚定节奏和表达逻辑，默认改写，不是必须复现的台词。

声线在构筑期依据人格、经历、社会位置、关系接口、身体习惯与成人设定直接完成。导入材料没有提供现成对白时，主 Agent 仍须按人设补齐核心声线、对象覆盖与场景覆盖；需要例句时写作“校准示例”，它说明表达机制但不冒充正史事件。

故事正文、回合记录和其他会话都不是声线设定的证据源，不得据此归纳、升级或写回 Story Bible。正文若暴露 OOC，只能触发一次显式的构筑修订：重新从既有人设推演，或向用户确认真正需要改变的人格机制；不能把模型自己写出的重复模式循环训练成角色事实。冻结前不得保留“候选、待采样、待会话校准、例句未冻结”等临时状态。

口头禅、内部笑话和回环意象单列为“回环梗”，不作为核心声线证据。一句俏皮话即使在近期正文出现多次，也不能自动升级为人格；记录它的作用、触发、别名与变化方向，并让会话台账负责冷却。

## 冻结标准

当以下内容足以支撑连续写作时即可冻结：

- 主要人物能做出彼此不同且可预测的选择。
- 世界能对选择施加具体后果。
- 核心关系具有可持续变化空间。
- 重要名词、能力和历史不存在妨碍写作的冲突。
- 不确定处被明确标为留白，而非遗漏。

冻结前先运行：

```bash
story_studio.py bible finalize --project <项目>
```

默认只生成审计结果，检查空骨架、过时“待构筑”、后台声明、空禁区、跨文件重复、锚点角色／声线、NSFW 兑现度以及项目入口状态。主 Agent 审核并修正后再运行：

```bash
story_studio.py bible finalize --project <项目> --apply
```

`--apply` 只在没有阻塞错误时将 `bible_status` 改为 `frozen`，同步 `00-项目索引.md` 与 `构筑/构筑状态.md`，重建检索索引并运行结构验证。随后再创建 Git 里程碑。

冻结时保留 `构筑/原始StoryBible.md`。未确定但不妨碍稳定写作的内容改列为“有意留白”，不要继续以“待构筑”留在冻结正史中。
